Project 8 · complete

Teaching a tiny model arithmetic with GRPO

We take Project 1's small GPT (13.9M parameters, trained only on children's stories) and post-train it with GRPO, the reinforcement-learning method behind recent "reasoning" models, on arithmetic problems whose answers a program can check. Everything is written by hand and runs on a CPU.

Question: with the same compute, does GRPO make the model more accurate than plain supervised fine-tuning?

Answer: GRPO works (+15 points from a half-trained start), but spending the same time on more supervised training works far better (+38 points). From a fully trained start GRPO has almost nothing left to learn from.

Start here: the basic ideas

Two ways to teach a model

Supervised fine-tuning shows the answer. Reinforcement learning only says "good" or "bad".

Supervised fine-tuning (SFT): we show the model a question and a correct worked solution and train it to predict every token of that solution. The model gets a correction on every token.

Reinforcement learning (RL): the model writes its own answer, a program checks it, and the model gets one number back: the reward (here 1 if the final number is right, plus 0.1 if the answer is well formed). The model has to work out which of its own choices led to the reward.

SFT is a teacher writing out the full solution for you to copy. RL is a teacher who only marks your answer right or wrong. The second is much less information per question, but it works even when nobody knows how to write the solution.

GRPO in one picture: compare answers to the same question

Group Relative Policy Optimization asks the model the same question several times and compares the answers with each other.

1. ask one question 8 times→ 2. reward each answer→ 3. advantage = reward − group average→ 4. make above-average answers more likely, below-average less

Step 3 is the clever part. There is no separate "critic" model to predict how good an answer should be: the group's own average is the yardstick. It also has a catch, which became the main story of this project: if all 8 answers get the same reward, every advantage is zero and the model learns nothing from that question.

Try it: click an answer to mark it right or wrong
Question: 34 + 59 - 18 = ? (true answer 75)
Advantage = (reward − group mean) ÷ group standard deviation; the 0.1 format bonus is included. A rare correct answer in a mostly-wrong group gets a big push; a group where all answers agree gets none.

The task: checkable arithmetic

Five kinds of problems, one or two steps each, so every answer and every step can be checked by a program.

Families: addition/subtraction, multiplication, 3-number chains (12 * 4 - 9), one-step word problems, two-step word problems. 100,000 training, 500 validation, 1,000 test problems, split by a hash so no test problem (or the same problem with operands swapped) ever appears in training.

The 16 phases

1

Environment

a clean, recorded setup

What we did

New folder project8 with its own virtual environment (PyTorch 2.14.1, CPU), a frozen package list, and scripts/env_report.py recording Python 3.12.10, 24 CPU threads and 63.7 GB RAM. Project 1's model and tokenizer are read from ../project1 and never modified (checked by sha256).

Why

RL results move with small details (seeds, versions, thread counts). Recording them first makes every later number reproducible.

Decision

No GPU, so GRPO is written by hand in PyTorch instead of using an RL library built for GPUs. That also makes every part of the algorithm visible.

2

A checkable task

rewards a program can compute

What we did

grpo/tasks.py generates 5 problem families with numbers small enough for a 13.9M model. Each problem has a "chain" (e.g. 3*4=12;12-5=7). The split into train / validation / test is a hash of that chain with commutative operands sorted, so 3 + 5 and 5 + 3 always land in the same split.

Result

100,000 training, 500 validation and 1,000 test problems, zero overlap (checked by an assertion). Test: 476 one-step and 524 two-step problems.

Problem found: multiplication first had too few unique problems to fill the test set. We widened the range (2–12 × 2–99) and made the chain canonical before generating anything else.
3

Answer format and a strict parser

no partial credit for sloppy answers

What we did

Every answer must end with Final answer: <answer>N</answer>. grpo/answer_parser.py accepts exactly one tag with one number and labels every failure: no tag, unclosed tag, two different answers, not a number, too long.

Why

An RL model will exploit any loophole in its reward. A lenient parser ("take the last number in the text") could pay for answers that list many numbers. Strict parsing closes that door.

4

Baseline: the original model

where we start

Result

0% accuracy, 0% valid format. The story model just keeps writing a story after "Solution:".

Decision

GRPO cannot start here: if no answer is ever right, every group has reward 0 and every advantage is 0. We need a supervised warm-up first.

5

SFT warm-up

teach the format and the basics by example

What we did

3,000 updates × 64 worked solutions (38 minutes), loss only on the solution tokens, learning rate 3e-4 decaying to 3e-5. Checkpoint and validation every 250 updates.

Result

Decision

The final SFT model is almost perfect, so GRPO from it might have nothing to learn. Before running any GRPO, we added a second starting point, SFT update 1,000 (55%), and wrote that change into the hypotheses file. The original plan was kept unchanged alongside it.

6

Reward

what "good" means

What we did

reward = 1.0 × correct + 0.1 × valid format. The format bonus is small, so a well-formatted wrong answer (0.1) is always worth much less than a correct one (1.1).

A small mark for neat handwriting, a big mark for the right answer. Neatness alone never passes the test.
7

Grouped sampling

8 answers per question, fast

What we did

grpo/policy.py samples 16 questions × 8 answers = 128 answers at once, at temperature 1.0, with a key-value cache (each new token reuses the work done for earlier tokens). Prompts of different lengths are padded on the left so all answers start at the same position, and the position numbers count only real tokens.

Why it matters

Generating answers is the slowest part of RL: tokens must be written one after another. Batching 128 answers made one GRPO iteration take 2–3.5 seconds instead of minutes.

8

Group-relative advantages

better or worse than the group?

What we did

advantage = (reward − group mean) / (group std + 1e-6). Groups where all rewards are equal get advantage 0, and their share is logged every iteration. That number, "zero-variance groups", became the key diagnostic.

Try the demo at the top: one right answer among eight gets advantage +2.6; seven right and one wrong gives the wrong one −2.6 and each right one only +0.38.
9

The GRPO objective

a careful, limited step

What we did

grpo/grpo_loss.py: for every answer token, the ratio between the new and old probability of that token, multiplied by the answer's advantage, with the ratio clipped to [0.8, 1.2] so one update cannot move too far. Plus a KL penalty (β = 0.04) that pulls the model back toward the starting model. Each batch of 128 answers is used for 2 passes of 2 updates.

Clipping is a speed limit per update; the KL penalty is a rubber band tying the model to where it started.

Check

Unit tests: answers with zero advantage give zero gradient; a clipped token gives no gradient; KL is 0 at the reference. 46 tests in total.

Main runs (300 iterations, 38,400 answers each)

  • From the final SFT model: about 90% of groups are all-correct for the whole run; the reward stays flat at 1.07.
  • From SFT update 1,000: about half the groups have signal; reward rises 0.70 → 0.84; validation 54% → 68–72%. Training is stable: about 0.1% of tokens clipped, answer length unchanged.
Lesson: the learning rate, not the clipping, kept GRPO stable. At 1e-4 the model broke within 20 iterations even with clipping.
11

Fair baselines

what would the same time buy otherwise?

What we did

A GRPO gain only counts if it beats the obvious alternative. Fixed before testing:

  • more SFT, same time for each starting point: for the early start, the SFT checkpoint whose extra time after update 1,000 is closest to GRPO's (update 2,250: 941 s vs 1,012 s); for the final start, 819 more SFT updates (564 s vs 618 s).
  • a lower sampling temperature (0.7): RL often just makes a model more confident, which a lower temperature does for free.
Both "more SFT" controls got slightly less time than GRPO, so the comparison leans in GRPO's favour.

What it means

GRPO really learns when there is signal: it beats the temperature trick and improves greedy answers by 10–12 points. But here correct worked solutions are free, and SFT learns from every token of them, so imitation wins by a wide margin. GRPO's real strength is for tasks where you cannot write the solution, only check it.

Seeds matter as much as the ablation: compared with seed 0 only, removing the format bonus or the KL penalty looks significantly worse. Compared with seeds 1 and 2 it makes no difference. A one-seed ablation would have reported a false finding.

The KL penalty did nothing measurable: measured afterwards, the model moved the same distance from its start with it (0.0167 per token) and without it (0.0170). At this small learning rate the model barely moves, so the rubber band is never pulled. More SFT moved it twice as far, and to a much better place.

Error analysis

every step checked automatically

Each of the 16,000 answers per system is compared step by step with the true computation.

arithmetic error (97% of all mistakes)
Question: 8 + 87 = ?
8 + 87 = 85.
Final answer: <answer>85</answer>
"lucky": right answer, wrong steps (1–2% of correct answers)
Question: 88 + 91 - 86 = ?
88 + 91 = 189. 189 - 86 = 93.
Final answer: <answer>93</answer>
Two wrong steps cancel out (88 + 91 is 179; 189 − 86 is 103), and the final answer 93 happens to be right.
  • The model almost always sets up the right steps; what it gets wrong is the addition or multiplication itself. GRPO makes those errors rarer (7,153 → 4,619) but does not change their kind.
  • The reward only checks the final number, so "lucky" answers are paid in full. GRPO did not learn to exploit this: they fell from 2.1% to 1.2% of correct answers.
  • GRPO makes answers more uniform: different answers per 16 samples fell from 4.6 to 3.1. More SFT does that even more (1.6).

Every random choice has a fixed seed; all training logs, evaluations, every generated answer and the figures are saved under results/. Checkpoints (55 MB each) are rebuilt by the scripts.

Lessons learned (useful for any ML project)

  1. RL needs a model that is sometimes right and sometimes wrong. Watch the share of groups with no signal. Too weak or too strong a model gives GRPO nothing.
  2. Always compare with "the same compute spent on the simple thing". GRPO's +15 points looked great until more SFT gave +38 in the same time.
  3. Check the cheap trick. A lower sampling temperature beat GRPO from the final SFT model with no training at all.
  4. Run more than one seed before believing an ablation. Seed-to-seed spread (1.4 points) was as big as most ablation effects.
  5. Write predictions down first. 7 of 11 failed; because they were pre-registered, that is information, not embarrassment.
  6. Make every step checkable. Automatic step checking showed the errors are arithmetic, not planning, and that GRPO did not learn to game the reward.

Glossary

Advantage
How much better an answer did than the average answer to the same question (in GRPO, divided by the group's spread).
Clipping
Limiting how much one update can change the probability of a token (here to ±20%).
GRPO
Group Relative Policy Optimization: RL that compares several answers to the same question instead of training a separate critic.
Greedy decoding
Always choosing the most likely next token: one deterministic answer.
KL divergence
A measure of how different two probability distributions are; here, how far the trained model has moved from its starting point.
Matched compute
Giving two methods the same training time (or cost) before comparing them.
pass@k
The chance that at least one of k sampled answers is correct; it measures what the model can find.
Policy
RL's name for the model that chooses actions; here, the language model choosing tokens.
Reward
The score a program gives an answer: 1 for correct, plus 0.1 for valid format.
Sampled accuracy
The average correctness of answers drawn at random from the model (temperature 1.0).
SFT
Supervised fine-tuning: training on correct example solutions.
Temperature
A knob on sampling: below 1 makes the model pick likely tokens more often (more confident), above 1 more random.
Zero-variance group
A question whose sampled answers all got the same reward; GRPO learns nothing from it.
